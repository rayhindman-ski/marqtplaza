# BR-06 — Accessible discovery and navigation

## Enhancement assessment

**Priority:** P0 — Release gate

**Criticality:** Critical

**Complexity:** Very high

**Estimated effort:** 15–25 person-days (provisional)

This estimate covers the full existing implementation specification, not only copy: semantic and labelled controls, keyboard and screen-reader behavior, focus and announcements, contrast, reflow, zoom, touch targets, reduced motion, map-independent discovery, bilingual accessible names, guest/account states, and acceptance testing. Risk is critical because barriers can block core discovery entirely; complexity is very high due to cross-cutting remediation and multi-modal verification across every affected screen and state. P0 is a proposed release gate for affected v0.4 journeys, not a verified production emergency or user-approved deadline.

**Work packages**

- Accessibility audit and remediation design: **3–5 person-days**
- Semantics, focus, naming, and announcement implementation: **5–8 person-days**
- Reflow, input, and map-equivalent interaction remediation: **4–7 person-days**
- Assistive-technology and cross-state QA: **3–5 person-days**

**Estimation basis and exclusions:** The range excludes global rollout or dataset acquisition, ongoing verification operations, and third-party or legal lead times. Existing core search, authentication, and data contracts are presumed reusable; if they are absent or materially incompatible, re-estimate. Person-days are combined design, engineering, and QA effort, not elapsed delivery time, and overlap across BRs must not be summed blindly. ## Status and authority

- **Status:** Proposed implementation specification; not implemented or verified behavior.
- **Source of truth:** `requirements.md`, BR-06.
- **Business requirement:** “The experience must address accessibility barriers involving icon names, focus, contrast, semantics, and map-only discovery.”
- WCAG 2.2 AA is the target; any numerical design values below are proposed delivery targets, not measured facts.
- The live consumer stack and accessibility baseline must be inspected during implementation.
- The workspace report viewer and weekend guide are not the live consumer application.
- Proposed interfaces must be reconciled with existing components and contracts.

## Objective

Provide equivalent, understandable discovery and navigation for keyboard, screen-reader, low-vision, touch, motion-sensitive, and location-permission-denied consumers.

## Scope

- Accessible names for icons and controls.
- Logical semantics, headings, landmarks, focus order, focus visibility, and status announcements.
- Hague-only availability is explicit, and list-first discovery does not depend on a map, map SDK, pointer precision, or geolocation.
- Contrast, reflow, zoom, target sizing, reduced motion, and error identification.
- Dutch-English parity for accessible names and instructions.
- Accessibility across guest and account states.

## Non-goals

- Claiming formal conformance before an audit.
- Replacing native browser or assistive-technology behavior.
- Requiring consumers to disclose disability or accessibility preferences.
- Making map gestures the only way to select geography.
- Changing result ranking solely for presentation.
- Solving accessibility defects in non-consumer workspace artifacts.

## Accessibility principles
1. Native semantic elements are preferred over ARIA recreation.
2. Every interactive control has a visible or programmatic name matching its purpose.
3. Visual order, DOM order, and keyboard order remain coherent.
4. Focus is never removed, obscured, or moved without a user-triggered context change.
5. Information is not conveyed by color, position, sound, or icon alone.
6. List discovery remains primary and map use remains optional.
7. Geolocation is requested only after **Use my location**.
8. Manual neighbourhood selection remains available before and after denial.

## Target screens

1. **Global header/navigation:** labelled destinations, locale selector, and account entry.
2. **Search form:** explicit label, scope explanation, submit action, and validation.
3. **Neighbourhood/category browse:** semantic lists independent of map.
4. **Results list:** heading, count/status announcement, filters, cards, and **Show map**.
5. **Optional map panel:** named region, non-map equivalent, loading/error/hide controls.
6. **Place detail:** structured headings, metadata, caveats, and next actions.
7. **Privacy/account dialogs:** labelled dialogs with predictable focus return.

## Interaction flows

### Flow 1 — Keyboard search

1. **Entry:** Keyboard user enters at the page start.
2. **Action:** Skip link moves focus to main content; subsequent Tab follows visual order.
3. **UI response:** Search has a persistent label and visible focus.
4. **Submit:** Loading is announced without moving focus.
5. **Success:** Results heading/count is announced once and receives focus only when appropriate.
6. **Back:** Browser Back restores criteria and a meaningful focus target.
7. **Error/retry:** Error is associated with the search region; Retry is reachable.

### Flow 2 — Non-map neighbourhood browse

1. **Entry:** Consumer opens neighbourhood browse.
2. **Action:** Selects a named neighbourhood link/button.
3. **UI response:** List results load without map resources.
4. **Persisted state:** Valid criteria enter canonical history.
5. **Cancel:** Clearing selection returns focus to the initiating control.
6. **Permission denied:** No effect because geolocation was not required.

### Flow 3 — Optional map

1. **Entry:** Results list is already usable.
2. **Action:** Consumer activates **Show map**.
3. **UI response:** Map code loads; status is announced politely.
4. **Success:** Map region has a name and instructions; equivalent result links remain in the list.
5. **Hide:** **Hide map** unloads or conceals the panel and returns focus predictably.
6. **Error:** Map error does not remove, disable, or reorder list content.

### Flow 4 — Use my location

1. **Entry:** Consumer sees manual neighbourhood and **Use my location** options.
2. **Action:** Permission request occurs only after activating **Use my location**.
3. **Success:** Approximate resolved context is announced and editable.
4. **Denied/unavailable:** Plain-language message appears with manual alternative.
5. **Retry/cancel:** Retry is explicit; cancel retains existing criteria.

### Flow 5 — Locale and account transition

1. **Action:** Consumer changes locale or signs in.
2. **UI response:** Accessible names and status copy change consistently.
3. **Persisted state:** Public criteria remain; focus moves to a corresponding control.
4. **Failure:** Sign-in failure preserves guest browsing context and announces the error.

## State requirements

| State | Accessible behavior |
|---|---|
| Initial | One clear H1, landmarks, skip link, labelled search, local-only scope. |
| Loading | `aria-busy`/status pattern as appropriate; controls are not unnecessarily disabled. |
| Success | Results count/context announced once; cards retain semantic structure. |
| Empty | Descriptive heading and criterion-removal actions, not color-only indication. |
| Error | Error summary/message identifies cause and recovery; focus is managed intentionally. |
| Permission denied | Manual neighbourhood path remains visible and focused recovery is offered. |
| Guest | Full discovery remains keyboard/screen-reader usable without sign-in. |
| Account | Additional controls have names, states, and no focus-order disruption. |
| Map hidden | No map resources required; list is complete. |
| Reduced motion | Nonessential animation is removed; no information depends on motion. |

## Desired and undesired behavior

| Desired | Undesired |
|---|---|
| Icons have localized accessible names and visible context. | Unlabelled icon-only controls. |
| Visible focus meets WCAG 2.2 AA target. | Removing outlines without equivalent focus styling. |
| Native links/buttons/forms are used. | Click handlers on non-semantic elements. |
| Results work without map or permission. | Map-only neighbourhood selection. |
| Map loads after explicit **Show map**. | Loading map SDK before list discovery. |
| Permission follows **Use my location**. | Permission prompt on page load. |
| Status changes are concise and announced once. | Repeated or interruptive live-region output. |
| Errors identify fields and recovery. | Color-only or silent failure. |
| 200% zoom and 320 CSS px reflow preserve use. | Clipped controls or two-dimensional page scrolling. |
| Locale switch preserves meaning and context. | English accessible names on Dutch controls. |

## Proposed component interfaces

These are proposed frontend interfaces, not current implementation claims.

```text
AccessibleIconControl {
  visibleLabel?: LocalizedString
  accessibleName: LocalizedString
  pressed?: boolean
  expanded?: boolean
  controlsId?: string
}

DiscoveryStatus {
  state: initial | loading | success | empty | error
  localizedMessage: string
  resultCount?: number
}
```

- Search/navigation state uses the canonical public URL: city, neighbourhood, query, category, filters, scope, locale.
- URLs exclude coordinates, private preferences, account identifiers, and tokens.
- Invalid parameters are safely normalized or rejected with an understandable message.
- Accessibility preferences should remain local unless account sync is explicitly consented to and documented.

## Technical implementation plan

### Audit and architecture

1. Inspect live routes, components, rendered DOM, CSS tokens, router, map loading, and localization.
2. Inventory controls, names, roles, landmarks, heading levels, dialogs, live regions, and focus transitions.
3. Establish automated linting and component-level accessibility checks without treating them as full conformance.
4. Define manual browser/assistive-technology coverage for supported platforms.

### Frontend

5. Replace non-semantic interactive elements with native controls where possible.
6. Add localized visible labels; use accessible-only labels only where visible text would be redundant.
7. Implement skip links, coherent landmarks, headings, and DOM order.
8. Create a visible focus token satisfying WCAG 2.2 AA focus requirements.
9. Verify text/non-text contrast against WCAG 2.2 AA; adjust tokens rather than one-off overrides.
10. Ensure minimum target size meets the applicable WCAG 2.2 AA criterion or has sufficient spacing/exceptions.
11. Make validation programmatic, descriptive, and associated with affected fields.
12. Implement restrained live-region announcements for loading, count, empty, and error states.
13. Retain list discovery before and after optional map loading/failure.
14. Request geolocation only from **Use my location** and return focus after denial.
15. Respect `prefers-reduced-motion` and avoid forced animation.
16. Support text resizing, zoom, 320 CSS px reflow, orientation changes, and touch.

### Integration, privacy, and rollout

17. Reconcile component interfaces with the existing design system and router.
18. Preserve canonical criteria and focus context across browser history.
19. Do not record assistive-technology use, permission denial, or precise location in analytics.
20. Test Dutch and English visible/programmatic names in the same release.
21. Run automated checks in CI and manual keyboard, screen-reader, zoom, contrast, mobile, and permission tests.
22. Roll out by route behind a flag; block full exposure on critical keyboard or screen-reader defects.

## Acceptance criteria

1. **BR-06-AC-01:** All interactive controls expose accurate localized names, roles, values, and states.
2. **BR-06-AC-02:** Keyboard order is logical; focus remains visible and is never trapped or lost.
3. **BR-06-AC-03:** Consumers can complete neighbourhood/category discovery without loading a map or granting permission.
4. **BR-06-AC-04:** Map resources load only after **Show map**; failure leaves equivalent list content usable.
5. **BR-06-AC-05:** Geolocation prompts only after **Use my location**, with a manual alternative after denial.
6. **BR-06-AC-06:** Loading, success, empty, error, and permission states are programmatically conveyed without excessive announcements.
7. **BR-06-AC-07:** Text, controls, focus indicators, and meaningful graphics meet applicable WCAG 2.2 AA contrast criteria.
8. **BR-06-AC-08:** Content remains usable at 200% zoom and 320 CSS px width without loss or page-level two-dimensional scrolling.
9. **BR-06-AC-09:** Errors are identified in text, associated to controls, and include a keyboard-reachable recovery.
10. **BR-06-AC-10:** Canonical history restores criteria and a meaningful focus position without private URL data.
11. **BR-06-AC-11:** Guest and account discovery provide equivalent accessibility.
12. **BR-06-AC-12:** New visible and programmatic copy has Dutch-English parity.
