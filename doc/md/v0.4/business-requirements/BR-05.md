# BR-05 — Relevant local context

## Enhancement assessment

**Priority:** P1 — High

**Criticality:** Medium

**Complexity:** Medium

**Estimated effort:** 6–10 person-days (provisional)

This estimate covers the full existing implementation specification, not only copy: Hague availability, neighbourhood and category browse, dated examples with trust metadata, canonical criteria, list-first behavior, bilingual presentation, and acceptance testing. ## Objective

Make The Hague context immediately recognizable and useful by showing supported neighbourhoods, locally meaningful categories, and dated examples without requiring a map, location permission, or an account.

## Scope

- State that current availability is limited to The Hague.
- Offer a visible neighbourhood browse path and locally relevant categories.
- Show current examples with source, checked-on date, and status fields.
- Carry city, neighbourhood, category, query, filters, scope, and locale through results and shared URLs.
- Support Dutch and English parity for all new labels and content metadata.
- Preserve a list-first discovery path; map use is optional and explicitly initiated.

## Non-goals

- Expanding live coverage beyond The Hague.
- Inferring a neighbourhood from precise coordinates without consent.
- Guaranteeing completeness, opening hours, availability, allergy safety, or merchant quality.
- Adding unsupported verification badges.
- Replacing BR-03 list discovery, BR-04 scope controls, or BR-10 result actions.
- Treating editorial examples as paid rankings without clear disclosure.

## Target screens

1. **Homepage local-context module:** The Hague availability statement, neighbourhood links, category links, and current examples.
2. **Neighbourhood directory:** alphabetical/localized list with result counts only when trustworthy and current.
3. **Category directory:** locally relevant categories with plain-language descriptions.
4. **Results list:** visible active context, source-group labels, freshness fields, and optional **Show map** action.
5. **Place detail:** neighbourhood, category, source, checked-on date, status, and unknown values.
6. **Unsupported-city state:** clear Hague-only message and a path back to The Hague browsing.

## Interaction flows

### Flow 1 — Browse a neighbourhood

1. **Entry:** Consumer opens a fresh homepage session.
2. **UI state:** Page states current availability is The Hague and shows neighbourhood choices without requesting location.
3. **Action:** Consumer selects a neighbourhood.
4. **UI response:** A list view loads; the map remains unloaded until **Show map** is selected.
5. **Persisted state:** Canonical URL records `city`, `neighbourhood`, `scope`, and `locale`.
6. **Back:** Browser Back returns to the same browse position and criteria.
7. **Cancel:** Clearing the neighbourhood returns to Hague-wide local results.
8. **Retry:** A failed load keeps the selection visible and offers Retry.

### Flow 2 — Browse a local category

1. **Entry:** Consumer selects a category from the homepage or directory.
2. **Action:** Consumer optionally adds a neighbourhood.
3. **UI response:** Results identify both category and geographic context.
4. **Persisted state:** URL records `city`, `category`, optional `neighbourhood`, filters, scope, and locale.
5. **Back/cancel:** Removing one criterion retains all others; Back restores the prior combination.
6. **Retry:** Error recovery does not reset criteria.

### Flow 3 — Open a current example

1. **Entry:** Consumer activates an example card.
2. **UI response:** Detail shows source, checked-on date, status, and explicit `Unknown` values.
3. **Action:** Consumer follows an available next action or returns to results.
4. **Persisted state:** Return navigation restores list position and criteria.
5. **Failure:** Unavailable detail shows an explanation and a return path; it does not fabricate content.

### Flow 4 — Optional map

1. **Entry:** Consumer is already using list results.
2. **Action:** Consumer selects **Show map**.
3. **UI response:** Map resources begin loading with a named loading status.
4. **Success:** Map reflects current public criteria; list remains usable.
5. **Permission:** Map browsing itself requires no geolocation permission.
6. **Cancel/error:** Hiding or failing the map leaves list results intact.

### Flow 5 — Unsupported city

1. **Entry:** Consumer supplies a non-Hague city through a URL or input.
2. **UI response:** Interface states that current availability is The Hague.
3. **Action:** Consumer chooses **Explore The Hague** or edits the location.
4. **Persisted state:** Invalid city values are not silently converted.

## State requirements

| State | Required behavior |
|---|---|
| Initial | Show Hague-only availability, neighbourhoods, categories, and local-only default scope. |
| Loading | Preserve criteria; announce loading text; avoid loading the map. |
| Success | Show relevant list results and active geographic/category context. |
| Empty | Explain that no matching local entries were found; offer criterion removal, not invented examples. |
| Error | Name the failed operation, retain criteria, and provide Retry. |
| Permission denied | Continue list and manual-neighbourhood discovery unchanged. |
| Guest | Permit all browsing, searching, sharing, and detail viewing. |
| Account | Provide the same discovery plus account features defined elsewhere. |
| Stale/unknown | Display checked-on/status metadata or explicitly show `Unknown`. |
| Unsupported city | State Hague-only availability and provide a deliberate recovery action. |

## Desired and undesired behavior

| Desired | Undesired |
|---|---|
| The Hague coverage is explicit. | Implying nationwide coverage. |
| Neighbourhoods are usable without a map. | Requiring map SDK or permission before discovery. |
| Categories use understandable local language. | Generic or untranslated taxonomy labels. |
| Examples have source/date/status metadata. | Presenting undated examples as current. |
| Unknown values are shown as unknown. | Guessing freshness, status, or provenance. |
| Fresh sessions search local-only. | Silently including web results. |
| Web results require explicit opt-in and source grouping. | Mixing local and web results without labels. |
| Shared URLs contain public search criteria only. | Encoding coordinates, private preferences, or tokens. |
| Back navigation restores context. | Resetting criteria or scroll position unexpectedly. |
| Map is lazy-loaded after **Show map**. | Blocking list results on map loading. |

## Proposed data and API contracts

These interfaces are proposals and must be reconciled against inspected live contracts.

```text
LocalContext {
  city: { id, localizedName, availabilityStatus }
  neighbourhoods: [{ id, slug, localizedName, status }]
  categories: [{ id, slug, localizedName, localizedDescription, status }]
  examples: [{ placeId, title, neighbourhoodId, categoryIds,
               source, checkedOn, status }]
}
```

- Proposed `GET /api/discovery/context?city=the-hague&locale=en|nl`.
- Proposed `GET /api/places?city=&neighbourhood=&category=&query=&filters=&scope=&locale=`.
- `checkedOn` should be an ISO 8601 date when known; absence must map to visible `Unknown`.
- `source` and `status` are field-level metadata, not a blanket verification claim.
- Canonical shared URL permits only city, neighbourhood, query, category, filters, scope, and locale.
- Parameter values must be allowlisted, length-limited, normalized, and safely rejected when invalid.
- Coordinates, private preferences, account identifiers, and tokens must never enter shared URLs.

## Technical implementation plan

### Discovery and content

1. Inspect the live consumer stack, routes, schemas, search provider, localization system, and content ownership.
2. Inventory supported Hague neighbourhoods and categories from authoritative project data.
3. Define stable IDs/slugs separately from localized display names.
4. Define editorial ownership and freshness rules for examples.
5. Add visible Hague-only availability copy in both locales.
6. Ensure examples are real published records; do not seed production paths with mock content.

### Frontend

7. Build semantic neighbourhood and category lists using links or buttons with accessible names.
8. Add active-context chips/headings and a single clear criterion-removal behavior.
9. Render initial, loading, success, empty, error, and unknown states.
10. Keep list discovery operational without map SDK, map permission, or geolocation.
11. Load map code only after **Show map**; retain the list during loading and failure.
12. Implement localized canonical URL parsing and browser history restoration.
13. Preserve criteria and list position when returning from details.

### Integration and quality

14. Reconcile proposed endpoints and fields with existing contracts; version changes when needed.
15. Group local index results separately from opted-in web results.
16. Validate unsupported, duplicate, malformed, and untranslated taxonomy records.
17. Add telemetry only for consented, necessary aggregate events; exclude raw query/location where not required.
18. Meet WCAG 2.2 AA for semantics, focus, contrast, reflow, status announcements, and target size.
19. Verify Dutch-English parity for labels, descriptions, errors, dates, and URL behavior.
20. Roll out behind a configuration flag, validate Hague content, monitor errors/empty states, then expand exposure.

## Acceptance criteria

1. **BR-05-AC-01:** A fresh session visibly identifies current availability as The Hague.
2. **BR-05-AC-02:** Consumers can open list results by neighbourhood without map or location permission.
3. **BR-05-AC-03:** Supported local categories and neighbourhoods have stable IDs and Dutch-English labels.
4. **BR-05-AC-04:** Fresh-session searches default to local-only; web results require explicit opt-in and are grouped by source.
5. **BR-05-AC-05:** Each displayed example exposes source, checked-on date, and status, with unknown values explicit.
6. **BR-05-AC-06:** Map resources load only after **Show map** and map failure does not block list use.
7. **BR-05-AC-07:** Canonical URLs include only validated public criteria and restore equivalent results and labels.
8. **BR-05-AC-08:** Back, clear, cancel, and retry preserve all unaffected criteria.
9. **BR-05-AC-09:** Unsupported cities receive an explicit Hague-only state without silent substitution.
10. **BR-05-AC-10:** Initial, loading, success, empty, error, permission-denied, guest, and account states are defined and usable.
11. **BR-05-AC-11:** New UI and copy meet WCAG 2.2 AA and Dutch-English parity.
12. **BR-05-AC-12:** No UI implies verification, safety, or freshness beyond field-level evidence.
