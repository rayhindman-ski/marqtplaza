# BR-02 — Clear navigation labels and hierarchy

## Enhancement assessment

**Priority:** P1 — High

**Criticality:** High

**Complexity:** Medium

**Estimated effort:** 5–8 person-days (provisional)

This estimate covers the full existing implementation specification, not only copy: information hierarchy, labelled desktop and mobile navigation, current-location cues, history/context preservation, account and locale entry points, focus behavior, and acceptance testing. Risk comes from regressions across responsive, guest/account, and bilingual states; complexity is medium because shared navigation and routing behavior must remain coherent across several journeys.

**Work packages**

- Information architecture and interaction design: **1–2 person-days**
- Responsive navigation, routing, and state implementation: **2–3 person-days**
- Accessibility, localization, and acceptance QA: **2–3 person-days**

**Estimation basis and exclusions:** The range excludes global rollout or dataset acquisition, ongoing verification operations, and third-party or legal lead times. Existing core search, authentication, and data contracts are presumed reusable; if they are absent or materially incompatible, re-estimate. Person-days are combined design, engineering, and QA effort, not elapsed delivery time, and overlap across BRs must not be summed blindly. ## Exact business requirement

> Navigation must provide sufficient labels and a clear hierarchy so consumers can understand the purpose of visible controls without relying solely on icons.

## Objective

Provide a predictable, labelled navigation system that tells consumers where they are, what each action does, and how to return, across desktop, mobile, Dutch, English, guest, and account states.

## Scope

- Global header and primary navigation labels.
- The visible “UserRole user” and language controls.
- Current-location indication, page titles, breadcrumbs where useful, and browser history behavior.
- Responsive navigation disclosure on narrow screens.
- Accessible names, focus behavior, landmarks, and control semantics.
- Canonical shared criteria in navigation between homepage, results, place detail, and account entry.

## Non-goals

- Defining account entitlements or registration value beyond the navigation entry point.
- Designing the result-card action hierarchy or place-detail information architecture.
- Requiring permanent text beside universally understood decorative imagery; every interactive icon still requires a programmatic and, where ambiguity exists, visible label.
- Adding new top-level destinations without validated user need.
- Changing availability beyond The Hague.
- Assuming that the current visible controls are wired to any particular backend.

## Proposed information hierarchy

1. **Global header:** MarqtPlaza home link, primary destinations, language control, and clearly labelled account entry.
2. **Page context:** one page `h1`, optional breadcrumb only when it aids return from nested content.
3. **Discovery and content:** query, filters, list/map choice, and list-first results remain separate from global navigation.
4. **Secondary/footer navigation:** privacy, accessibility, language, and service information.

No discovery filter, map action, or role label should masquerade as a primary destination.

## Target screens

1. **Desktop guest homepage:** labelled primary destinations, language control, and “Sign in” or equivalent account label.
2. **Desktop account state:** account control labelled with its purpose; role implementation details are not exposed as consumer copy.
3. **Mobile header collapsed:** one labelled menu trigger with the same destination set and clear current state.
4. **Navigation panel open:** focus-contained when modal, dismissible, and scroll-safe.
5. **Results and place detail:** current page and return hierarchy are identifiable; discovery criteria persist.
6. **Dutch locale:** all visible and programmatic navigation labels have equivalent Dutch wording.

## Numbered interaction flows

### Flow 1 — Navigate from homepage to a primary destination

1. **Entry:** A guest lands on the homepage.
2. **UI state:** Logo/home, primary links, language, and “Sign in” have visible labels; active page is identifiable.
3. **Action:** The consumer activates a primary link.
4. **UI response:** The destination loads with one descriptive `h1`; focus moves predictably to the new page's main content or remains under browser-native navigation conventions.
5. **Persisted state:** Applicable shareable discovery criteria remain in the validated canonical URL.
6. **Back:** Browser Back restores the prior page and criteria.
7. **Error/retry:** A route failure provides a labelled retry and home action.

### Flow 2 — Use mobile navigation

1. **Entry:** A consumer opens the experience at a narrow viewport.
2. **Action:** The consumer activates the labelled menu trigger.
3. **UI response:** The navigation panel opens, exposes the same essential destinations, and places focus at a logical point.
4. **Selection:** Activating a destination closes the panel and navigates once.
5. **Cancel:** Escape, close, or permitted outside interaction closes the panel and returns focus to the trigger.
6. **Back:** Browser Back follows route history and does not unexpectedly reopen the panel.

### Flow 3 — Change language

1. **Entry:** The consumer opens the labelled language control.
2. **Action:** The consumer selects Dutch or English.
3. **UI response:** New navigation copy and page content switch together; the selected language is programmatically indicated.
4. **Persisted state:** `locale` is reflected in the canonical shareable state using the existing routing convention after inspection.
5. **Criteria:** City, neighbourhood, query, category, filters, and scope remain unchanged.
6. **Failure:** If localization loading fails, show a recoverable message rather than a mixed-language partial state.

### Flow 4 — Enter account flow without losing context

1. **Entry:** A guest has active search criteria.
2. **Action:** The guest selects the clearly labelled sign-in entry.
3. **UI response:** The account flow explains the destination; it does not expose “UserRole user” as consumer-facing account value.
4. **Cancel:** Cancelling returns to the same validated criteria.
5. **Success:** Signing in returns to the originating context where safe.
6. **Privacy:** Tokens and account identifiers never enter the canonical shared URL.

### Flow 5 — Choose list, map, or location

1. **Entry:** The consumer is in discovery.
2. **Action:** List remains available by default; “Show map” and “Use my location” are separate, clearly labelled actions.
3. **UI response:** Map code loads only after “Show map.”
4. **Permission:** Geolocation is requested only after “Use my location.”
5. **Denied/cancelled:** Manual neighbourhood selection and list browsing remain available.

## Shared URL and history requirements

- The canonical shared state may include only validated `city`, `neighbourhood`, `query`, `category`, `filters`, `scope`, and `locale`.
- It must exclude coordinates, location precision, private preferences, account identifiers, session data, and tokens.
- Unknown, duplicate, malformed, or overlong parameters must be safely rejected or normalized with an understandable recovery state.
- Back and Forward must preserve meaningful route and criteria changes.
- Navigation menus, dialogs, and ephemeral focus state must not pollute shareable URLs.
- The URL format is proposed and must be reconciled with live routes before implementation.

## Required states

| State | Proposed behavior |
|---|---|
| Initial | Current page and labelled primary destinations are apparent; list discovery does not initialize map or location. |
| Loading | The activated destination communicates progress without disabling unrelated navigation. |
| Success | One destination is current; page title and `h1` match its purpose. |
| Empty | Navigation remains usable; content-level empty guidance does not replace the page hierarchy. |
| Error | Route or content failure keeps home/back/retry actions available and labelled. |
| Permission denied | Navigation remains unchanged; manual neighbourhood and list alternatives stay available. |
| Guest | Account entry says “Sign in” or approved equivalent; browse/search remains available. |
| Account | Account menu is purpose-labelled and exposes only authorized actions; no internal role string is shown as navigation copy. |

## Desired and undesired behavior

| Desired behavior | Undesired behavior |
|---|---|
| Visible text explains ambiguous interactive icons. | Icon-only actions whose purpose requires guessing. |
| Programmatic names match visible labels. | Accessible names that conflict with visible copy. |
| One stable primary hierarchy across viewports. | Mobile destinations missing or reordered without reason. |
| Active page conveyed by more than color. | Color-only current-page indication. |
| Language switch preserves criteria. | Locale change resets search or creates mixed-language UI. |
| Guest search remains accessible. | Account link blocks discovery or implies registration is required. |
| Map and location are distinct explicit actions. | A navigation action silently requests location or loads map code. |
| Back restores meaningful context. | Custom navigation traps users or duplicates history entries. |

## Proposed technical implementation

### Frontend

1. Inspect current router, header, design system, authentication state, breakpoints, and localization mechanism.
2. Inventory every visible navigation control, destination, icon, accessible name, and state.
3. Define a single typed navigation model containing destination ID, route, translation key, visibility rule, and current-state matcher.
4. Render desktop and mobile variants from that model to prevent destination drift.
5. Replace consumer-facing internal-role strings with approved account-purpose labels.
6. Use semantic `header`, `nav`, `main`, lists, buttons, and links according to action behavior.
7. Add skip navigation, visible focus, current-page semantics, and deterministic focus restoration.
8. Keep discovery actions outside global navigation and lazy-load map dependencies after explicit activation.
9. Validate canonical parameters at the routing boundary.

### Proposed route/data interfaces

- Proposed route-state model: `{ city, neighbourhood?, query?, category?, filters?, scope, locale }`.
- Proposed navigation item model: `{ id, href, labelKey, icon?, audience, matchMode }`.
- Proposed session view model may expose `{ authenticationState, accountMenuItems }`; exact names and authorization rules must match existing contracts.
- No new API endpoint is assumed for navigation.
- Existing account, locale, and route contracts must be inspected; proposed models must be adapted rather than layered on incompatibly.

### Integration

- Coordinate labels with BR-01 proposition and BR-11 account value language.
- Keep BR-03 list browse reachable independently of map.
- Apply BR-04 scope terminology consistently in discovery navigation.
- Use BR-08 privacy decisions for locale persistence, analytics, and return URLs.
- Emit only necessary navigation event IDs; do not include query text, coordinates, tokens, or account data.

### Privacy and accessibility

- Target WCAG 2.2 AA, including keyboard access, focus visibility/not obscured, reflow, target size, names, roles, states, landmarks, and contrast.
- Do not rely on tooltips as the only label.
- Prevent focus from moving behind an open modal mobile menu; restore focus on close.
- Use an allow-listed local return path for account flows; reject external or malformed redirects.
- Ensure 320 CSS-pixel layouts avoid horizontal scrolling except intrinsically two-dimensional content.

### Rollout

1. Approve an English/Dutch label inventory and route map.
2. Validate guest and account variants against actual authorization behavior.
3. Introduce changes through the existing release-control mechanism, if present.
4. Run route, history, keyboard, screen-reader, zoom, touch-target, and locale regression checks.
5. Monitor destination errors and menu abandonment with privacy-minimized events.
6. Retain a rollback path that does not invalidate existing canonical links.

## Measurable acceptance criteria

1. **BR-02-AC-01:** Every interactive header icon has an accurate programmatic name, and every ambiguous primary action has a persistent visible text label.
2. **BR-02-AC-02:** Desktop and mobile navigation expose the same essential destinations and current-page indication.
3. **BR-02-AC-03:** Consumer-facing account navigation contains no unexplained internal role string such as “UserRole user.”
4. **BR-02-AC-04:** Each destination has one descriptive page `h1`, a matching document title, and a predictable route.
5. **BR-02-AC-05:** Mobile menu open, close, Escape, destination selection, and focus restoration work using keyboard and touch.
6. **BR-02-AC-06:** Language change preserves validated discovery criteria and produces no mixed-language new navigation copy.
7. **BR-02-AC-07:** Guest search and neighbourhood browse remain reachable without sign-in.
8. **BR-02-AC-08:** Map and geolocation are separate labelled actions and activate only after explicit selection.
9. **BR-02-AC-09:** Canonical URLs allow-list shareable criteria and exclude coordinates, private preferences, account identifiers, and tokens.
10. **BR-02-AC-10:** Back/Forward restores route and discovery criteria without reopening ephemeral menus.
11. **BR-02-AC-11:** Route loading, empty, error, and permission-denied states preserve usable global navigation.
12. **BR-02-AC-12:** Navigation meets agreed WCAG 2.2 AA checks in English and Dutch at desktop, mobile, and 200% zoom.
