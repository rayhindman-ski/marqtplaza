# BR-04 — Transparent search scope

## Enhancement assessment

**Priority:** P0 — Release gate

**Criticality:** High

**Complexity:** Medium

**Estimated effort:** 5–8 person-days (provisional)

This estimate covers the full existing implementation specification, not only copy: local-only defaults, informed web-result opt-in, source grouping, scope persistence across URLs/history/locales, partial-failure behavior, accessible semantics, and acceptance testing. The main risk is silently broadening a search or obscuring provenance; complexity is medium because one reversible scope choice must stay synchronized across controls, requests, result groups, and shared state. P0 is a proposed release gate for affected v0.4 journeys, not a verified production emergency or user-approved deadline.

**Work packages**

- Scope language and interaction design: **1–2 person-days**
- Scope state and grouped-result implementation: **2–3 person-days**
- URL and search integration: **1 person-day**
- Accessibility, localization, and state QA: **1–2 person-days**

**Estimation basis and exclusions:** The range excludes global rollout or dataset acquisition, ongoing verification operations, and third-party or legal lead times. Existing core search, authentication, and data contracts are presumed reusable; if they are absent or materially incompatible, re-estimate. Person-days are combined design, engineering, and QA effort, not elapsed delivery time, and overlap across BRs must not be summed blindly. ## Exact business requirement

> MarqtPlaza must clearly explain the meaning and effect of “Also search online,” including how its scope differs from local search.

## Objective

Enable consumers to make an informed, reversible choice between local-only discovery and local discovery supplemented by web results. Scope must be visible before search, preserved in safe shared state, reflected in result grouping, and explained without vague privacy or quality claims.

## Scope

- Rename or clarify “Also search online” as “Include web results” or approved equivalent.
- Define local-only as the fresh-session default.
- Explain what changes when web scope is enabled.
- Display local and web results in separate, labelled source groups.
- Preserve scope across search, filters, shared URLs, history, and locale changes.
- Cover loading, success, empty, error, permission-denied, guest, and account states.
- Provide Dutch-English parity and accessible control semantics.

## Non-goals

- Selecting a particular web search provider.
- Claiming local data is complete, verified, safer, or more accurate.
- Claiming web results are current, endorsed, or checked by MarqtPlaza.
- Defining ranking algorithms or commercial placement.
- Requesting geolocation as part of web opt-in.
- Blending source groups into one provenance-obscuring list.
- Expanding service availability beyond The Hague.

## Proposed scope definitions

| Scope | Definition |
|---|---|
| Local-only | Searches established local catalogue/integrated sources; fresh-session default; does not initialize map or location; never described as exhaustive, verified, or guaranteed current. |
| Include web results | Adds a separately labelled group after explicit choice; is not endorsement or verification; discloses external data-sharing implications; does not silently become a future fresh-session default. |

## Target screens

1. **Homepage, fresh session:** local-only selected, concise scope explanation, optional “Include web results.”
2. **Scope details disclosure:** plain-language definitions, source treatment, privacy link, and caveat.
3. **Local-only loading/results:** criteria and active scope visible.
4. **Local plus web results:** separately headed groups with independent status and provenance.
5. **Partial failure:** one group can succeed while another fails, with scoped retry.
6. **Empty local group:** refinements and explicit web opt-in, not automatic scope expansion.

## Numbered interaction flows

### Flow 1 — Search with the fresh local-only default

1. **Entry:** A consumer opens a fresh homepage session.
2. **UI state:** Local-only is visibly selected; “Include web results” is unselected.
3. **Action:** The consumer enters criteria and submits.
4. **UI response:** Local loading state appears; no map, geolocation, or web-provider request is initiated by default.
5. **Success:** A local source group renders with the active scope visible.
6. **Persisted state:** Canonical URL records the local scope and safe criteria.
7. **Back:** The homepage restores query and local scope.
8. **Retry:** Local failure retains criteria and scope.

### Flow 2 — Learn about and enable web results

1. **Entry:** The consumer sees the unselected web option.
2. **Action:** The consumer opens the scope explanation.
3. **UI response:** The interface explains additional sources, separate grouping, available provenance, and relevant data-sharing before activation.
4. **Action:** The consumer explicitly selects “Include web results.”
5. **UI response:** Selected state and changed scope are announced.
6. **Search:** Submission requests the proposed combined scope.
7. **Success:** Local and web groups are separately labelled; available source/date/status fields are displayed and unknown values say unknown.
8. **Cancel:** Deselecting returns to local-only without clearing other criteria.

### Flow 3 — Handle local empty state

1. **Entry:** A local-only search completes with no matches.
2. **UI response:** The interface says no match was found for current criteria, without implying no such places exist.
3. **Recovery:** It offers clear filters, category/neighbourhood changes, and optional web opt-in.
4. **Action:** Web results run only if the consumer explicitly opts in.
5. **Back/cancel:** Criteria remain intact if the consumer declines or navigates back.

### Flow 4 — Handle independent source-group failure

1. **Entry:** Combined scope is selected.
2. **UI response:** Local and web groups expose independent loading status.
3. **Partial success:** Successful local results remain usable if web search fails, and conversely where contracts permit.
4. **Error:** The failed group names the operation and provides a scoped retry.
5. **Retry:** Only the failed request is retried where API support allows.
6. **Cancel:** The consumer can disable web scope and continue locally.

### Flow 5 — Share, switch locale, and return

1. **Entry:** The consumer has query, neighbourhood, filters, and combined scope.
2. **Action:** Copy/open the canonical URL or switch locale.
3. **UI response:** Valid criteria and scope reconstruct; new copy is entirely in the selected locale.
4. **Privacy:** Coordinates, private preferences, account identifiers, and tokens are absent.
5. **Back/Forward:** Scope changes restore as meaningful history entries without duplicate submissions where cached state applies.

## Canonical state rules

- Proposed safe parameters are `city`, `neighbourhood`, `query`, `category`, `filters`, `scope`, and `locale`.
- Proposed scope values are `local` and `local_web`; exact names must be reconciled with existing contracts.
- Coordinates, location precision/history, private preferences, provider credentials, account identifiers, sessions, and tokens are prohibited in shared URLs.
- Inputs must be allow-listed, normalized, length-bounded, and encoded safely.
- Unsupported scope values fall back to local-only with a visible correction, not silent combined search.

## Required states

| State | Proposed behavior |
|---|---|
| Initial | Fresh session is local-only; concise distinction and details control are available. |
| Loading | Active scope and independently loading groups are announced; controls cannot accidentally double-submit. |
| Success | Source groups are distinct; available source/date/status appear at the appropriate field level. |
| Empty | State is scoped to local or web group; refinements appear; web search is never silently enabled. |
| Error | Failure names the affected group, preserves criteria, and provides scoped retry or local continuation. |
| Permission denied | Scope search remains usable; geolocation denial has no effect and manual neighbourhood remains. |
| Guest | Full local and optional web searching remain available without account. |
| Account | Same scope semantics; account preferences must not override the explicit fresh-session rule without approved policy. |

## Desired and undesired behavior

| Desired behavior | Undesired behavior |
|---|---|
| Fresh session visibly starts local-only. | Web scope preselected without a current explicit choice. |
| Scope explanation precedes external request. | Vague checkbox with hidden data-sharing consequences. |
| Local and web groups have separate headings/status. | Blended results with unclear provenance. |
| Empty local results offer optional web scope. | Automatic expansion to web results. |
| Partial failure preserves successful group. | Whole page replaced because one provider failed. |
| Unknown evidence values are labelled unknown. | Inferred dates, unsupported badges, or safety guarantees. |
| Scope survives safe sharing and history. | Scope lost on Back, locale change, or filter update. |
| Scope has no dependency on map or location. | Checking web scope triggers map/location behavior. |

## Proposed technical implementation

### Frontend

1. Inspect current search form, state initialization, storage, URL parsing, provider integration, result renderer, and locale files.
2. Replace ambiguous scope presentation with a fieldset or equivalent named group and a details disclosure.
3. Initialize fresh-session scope deterministically to local-only.
4. Keep scope independent from map visibility, geolocation permission, authentication, and result layout.
5. Render source groups from typed response data with independent loading, empty, error, retry, and pagination states.
6. Validate route scope before dispatching any request.
7. Announce scope and group-status changes through concise live status, avoiding repeated result-card announcements.
8. Add all English and Dutch copy atomically.

### Proposed API contracts

- Proposed request: `{ city, neighbourhood?, query?, category?, filters?, scope: "local" | "local_web", locale, cursorByGroup? }`.
- Proposed response: `{ groups: [{ id: "local" | "web", status, items, nextCursor?, error? }], notices }`.
- Proposed result evidence: field-level `{ value, source?, checkedAt?, status? }`, with unknown represented explicitly.
- Proposed error behavior supports group-level codes and retriable status.
- No assertion is made that these endpoints, enums, or fields exist; inspect and reconcile existing request, provider, pagination, caching, timeout, and error contracts.
- Backend must reject unsupported scope values and must not interpret omission as web opt-in.

### Integration

- BR-01 uses this distinction in the value proposition.
- BR-03 consumes scope while retaining map-independent list discovery.
- BR-07 governs evidence and caveats for each source.
- BR-08 governs external-provider disclosure, legal basis, retention, deletion, and analytics.
- BR-10 uses grouped scope in cards and filters.
- Instrument scope-explanation open, explicit opt-in/out, group success/error, and scoped retry without recording raw queries, coordinates, tokens, or private preferences.

### Privacy and accessibility

- Target WCAG 2.2 AA.
- Use a real labelled control with visible selected state; do not rely on color, position, or tooltip.
- Ensure the details disclosure and scope choice are keyboard and screen-reader operable with visible focus.
- Explain external recipient/category, purpose, and linked privacy details before web activation where applicable.
- Apply data minimization and defined retention; never place sensitive values in the URL or general analytics.
- Maintain Dutch-English parity for labels, caveats, statuses, and errors.

### Rollout

1. Document actual local and web integrations and current default behavior after inspecting the live source.
2. Approve plain-language Dutch and English scope definitions and privacy text.
3. Ship parser/backend validation before or with the frontend default.
4. Use the existing feature rollout mechanism if available; avoid parallel state models.
5. Test fresh/returning sessions, storage migration, blocked provider, timeout, malformed URLs, both locales, and guest/account states.
6. Monitor provider errors and opt-in comprehension signals using privacy-minimized events.
7. Ensure rollback preserves local-only safety and existing valid shared links.

## Measurable acceptance criteria

1. **BR-04-AC-01:** Every fresh session starts with local-only scope and an unselected “Include web results” control.
2. **BR-04-AC-02:** Plain-language details explain what local and web scope do, how groups differ, and that inclusion is not endorsement or verification.
3. **BR-04-AC-03:** No web-provider request occurs before explicit opt-in.
4. **BR-04-AC-04:** Combined searches show separately labelled local and web groups with independent status.
5. **BR-04-AC-05:** A local empty result never automatically enables web scope and offers explicit opt-in as one recovery choice.
6. **BR-04-AC-06:** Failure in one group preserves successful content and offers scoped recovery where supported.
7. **BR-04-AC-07:** Deselecting web scope removes its group without clearing city, neighbourhood, query, category, filters, or locale.
8. **BR-04-AC-08:** Canonical URL/history preserves validated scope and safe criteria while excluding sensitive values.
9. **BR-04-AC-09:** Invalid or missing scope cannot result in silent web opt-in; safe fallback is local-only.
10. **BR-04-AC-10:** Scope does not initialize map code, request geolocation, or require an account; permission denial leaves search intact.
11. **BR-04-AC-11:** Unknown source/date/status values remain explicit, and no unsupported verification or allergy-safety claim appears.
12. **BR-04-AC-12:** English and Dutch scope controls, disclosures, statuses, and errors meet agreed WCAG 2.2 AA checks on mobile and desktop.
